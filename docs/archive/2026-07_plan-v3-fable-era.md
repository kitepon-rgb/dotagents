## 目的

**期間限定の Fable 5 を「消える出力」でなく「残る構造と判断」に変換し尽くす。**

本計画は旧・共通化基盤プロジェクト（dotagents）の再利用。ここで作る規約・環境・知識基盤は、Fable 5 が使えなくなった後も全端末・全プロジェクトで長期間使う。

**本旨は「開発工場（環境）の最適化」＝全プロジェクトに共通して効く土台の整備**（ハブ・規約・標準・モデル配置・ツール・罠DB・ランブック・同期基盤）。**個々のプロダクトの品質監査・法務チェック・深いバグ探しは本計画の範囲外**——それは「工場」でなく「工場で作る製品の検品」であり、オーナーが個別に依頼した時だけ行う（オーナー明示 2026-07-04: 走りすぎ是正）。各プロジェクトへの介入は原則、①GitHub 同期 ②フォルダ構成の標準化 ③CLAUDE.md ブラッシュアップ＋リファクタ の3つに絞る。

## この文書の書法（聖典の掟）

- 全端末で使う聖典。**方針は理由ごと本文に書く。**「会話で決めた」「メモ参照」は禁止＝根拠そのものを書く。
- 端末非依存・絶対日付。どの端末のどのモデルが読んでも同じ判断に着地する自己完結記述にする。
- 方針変更はこのファイルへの diff として現れる（＝重大イベント）。日々の消化は docs/TODO.md 側の diff（＝ただの進捗）。**混ぜない**——分離しているのは、他端末が diff を見ただけで「方針が動いたのか、作業が進んだだけか」を判別できるようにするため。
- **改善するべき方針は、見つけたその場で必ず本聖典に書く（絶対のルール。オーナー指示 2026-07-04）**: 作業中に得た規約・作法・罠対処のうち方針級のものを、端末メモリ・TODO・会話・コミットメッセージに置いて終わらせるのは禁止。それらは他端末に届かない。書き先の振り分け——方針と理由=本聖典／全プロジェクト共通の作法=グローバル CLAUDE.md 正本（P0 で repo 管理化）／プロジェクト標準=docs/PROJECT_LAYOUT.md／再現可能な外部罠=caveat／調査事実=rag/。迷ったら本聖典に書いてから移す。

## 原則

1. **Fable の使い所は3種だけ**: ①判断が資産として残る作業（監査・敵対的検証・裁定） ②構造の敷設（安全網・CI・規約・テンプレ） ③翻訳（弱いモデルでも従える契約・手順への落とし込み）。仕様が固まった実装は今後も安価モデルで足りる。**この計画の実行自体にこれを適用する**（オーナー明示 2026-07-04・レートリミット＝Fable 窓は有限資源）: 標準化の物量（フォルダ移動・CLAUDE.md 起草・同期収容・機械的リファクタ・ギャップ採点）は implementer/Workflow（安価モデル）へ委譲し、統括（ベル）は仕様＋罠リスト＋検証コマンドの作成・裁定・diff レビュー・コミット/push に絞る。委譲の作法はグローバル CLAUDE.md「委譲の作法」に従う（file:line 仕様・「渡した前提も再検証せよ」の義務化・ディレクトリ非交差・commit 禁止）。
2. **GitHub が真実の源**: プロジェクトは端末を跨いで存在する。**全てのプロジェクト作業は fetch→照合→整合させてから**（2026-07-04 の実測でも main が幹から100コミット以上遅れたリポがあった）。作業後は必ず push で真実を返す。
3. **リポ内知識 ＞ 端末ローカル記憶**: プロジェクトの真実（設計・手順・規約）は repo の CLAUDE.md / docs / rag に置く。端末メモリ（`~/.claude/projects/*/memory`）は端末固有・私的な文脈だけ。端末横断プロジェクトの記憶分裂はこの昇格で解消する。
4. **全リポを残す前提を置かない**: 終わったプロジェクトはローカルから消してよい。ただし**削除の決定は必ずオーナーに提案→承認**（AI が勝手に消さない）。安全判定は P2 のトリアージ手順に従う。
5. 各タスクにラベル: **F**=Fable 品質が要る／**A**=安価モデル＋契約で可／**H**=人手（ログイン・削除承認等）。
6. **自作資産の終活**: 自作 skill / command / rule / 契約は、作成時期を問わず（**Fable 期に今作る物も含めて**）現行 Claude のネイティブ能力と突合してから残す。突合で負ける資産は延命せず廃止を提案する（廃止承認は常に H）。**見直しのトリガーはオーナー**——モデル世代交代の時期はオーナーが宣言する。資産見直しのカレンダー駆動はしない——見直しは判断コストが高く、トリガー情報（世代交代）はオーナーしか持たないため、定期化しても形骸化する。※判断を要しない**機械的な衛生作業**（メモリ棚卸し・rag Lint。叩くだけで回る）は月次カレンダーで回してよい（P4・原則10と整合。形骸化するのは「判断」の定期化であって「実行」の定期化ではない）。見直しを安くするため、各資産の冒頭に**前提行**を1行仕込む（例: `前提: Fable級統括／Sonnet級実装者（2026-07 時点）`）——宣言が出た瞬間、次のモデルが grep で再検討対象を機械的に列挙できる。実例: audit-gauntlet（2026-05 作）は、反証工程なし・「指摘は有限だから必ず収束する」という誤った保証（監査は非決定的で幻覚指摘が湧き得る）・外部プラグイン（ECC council）へのハード依存・直列限定、の4点で現行ネイティブ Workflow の下位互換だった。**2026-07-04 棚卸しのオーナー裁定: ultracode 型 Workflow を起動する薄い入口へ作り直しで決着**（名前と起動条件は資産として残し、下位互換の中身を捨てた）。同棚卸しで codex/throughline repo 版は廃止（全端末で shadow され未使用）、auto-deploy-on-push・polish-github はブラッシュアップの上で存続。
7. **依存は「窓」に限定し、「真実の保存」には置かない**（ビルド対バイの判定基準）: 類似機能の完全自作より、保守された外部パッケージに依存する方が安い——ただし依存を置いてよいのは交換可能な「窓」（ビューア・UI・変換器）まで。**知識・判断・規約の保存層は素の Markdown＋git**（依存ゼロ・全モデル可読・端末横断）に置く。根拠: 窓は流行が去れば替えればよいが、器に真実を入れると人質になる。適用例——**Obsidian**: 窓として採用可（本質は素の md の上の UI 糖衣。商用利用無料・git 同期は作者界隈公認。`.obsidian/` は端末固有につき gitignore）。**NotebookLM**: 器なので主脳不可（ノートは素のファイルでなく、公式 API は Enterprise 限定〔2026-07 時点〕）。rag/ の md を一方通行で食わせる人間用の窓（音声概要等）としてのみ可。**ECC 等のプラグイン**: ネイティブ機能で上位互換できるため新規導入しない。詳細根拠と一次ソース: `rag/second-brain/`。
8. **文書監査・重要判断の検証の標準型は ultracode 型**: 並列多視点 Find → Dedup → 指摘1件ごとの敵対的反証 → 網羅性 Critic。Claude ネイティブの Workflow / サブエージェントのみで実施する。もっともらしい指摘・提案ほど反証にかけ、生き残ったものだけ採用する（実績: 2026-07 NoveLore〔ローカル名 `~/Developer/Novel`・GitHub 名 `forklore`。以下同一プロジェクト〕監査 71採用/21棄却＝棄却側に「もっともらしいが危険な提案」が複数あった）。
9. **モデルはバージョン固定禁止**: 各モデルはバージョンアップするため、latest 型で指定する。役割→現行最強の対応表 **docs/MODELS.md** を唯一の参照点にし、各所にモデル名を書き散らさない（世代交代時の更新箇所を一箇所にする）。役割の骨格: 統括=現行最強推論／実装=安価高速枠／反証=強推論枠／外部併走=Codex CLI・Grok Build（Grok / Composer）。
10. **知識は還流させて育てる（第二の脳）**: 調査・研究を使い捨てにしない。外部仕様・文献は rag/ に固定し、**出力（回答・監査ダイジェスト・図解）も rag/ に還流**して複利で育てる。根拠: Karpathy「LLM Knowledge Bases」（2026-04）と国内実践者の**独立な収束**（詳細: `rag/second-brain/`）。運用規約: ①`rag/<topic>/raw/` に一次ソース（markitdown 等で変換。**rc でなくバイト数で成功判定**——JS ページは空を吐く）②LLM が要約・[[リンク]]・概念記事へコンパイル（**wiki の保守は LLM の仕事**。人間は読む・考えることに集中）③`rag/INDEX.md` に1行台帳（出典・取得日・確度）④定期 Lint（矛盾・欠落・連結の健全性チェック。メモリ棚卸しと同じ枠で）⑤選球眼——何を入れないかが質を決める ⑥人間用の窓は Obsidian（同期は git 相乗り。真実の源を二重化しない）。

主な作業（消化は docs/TODO.md の P0 節）: 収録済み資産の要否棚卸し（原則6・承認 H）／orchestrate・agents の収録と install.sh の agents グループ対応／グローバル CLAUDE.md 正本化（`~/.claude` を tar バックアップしてから。**install.sh は実ファイル存在時 SKIP するため、既存の実ファイル `~/.claude/CLAUDE.md` は退避・削除してから symlink を張る**——さもないと正本化が静かに不成立になる〔P1 の退避手順と同じ〕。正本化の際、オーナーへの応対規範を収録する——**質問・方針提示にはまず会話で応じ、オーナーの反応を待ってから手を動かす。承認ダイアログやツール連発を会話の代わりにしない**〔2026-07-04 オーナー指摘×3回。全端末の応対品質に関わる方針〕）／caveat 移管／MODELS.md・settings.fragments.md 新設／ツール標準化（原則7 で選定し、**現行ドキュメントで検証してから**、install.sh／README ランブックに焼き込む。**入れる＝標準に載せる**、ad-hoc インストール禁止）／install.sh 再実行と検証バッテリー。

## P2. Git 同期監査 ＋ リポの終活トリアージ【A(掃引)+F(判定)+H(削除承認)・初回2〜3h】

**P2 は「リポを触る作業」（P3 標準適用・P5 再生）に、リポ単位で先行する。** 端末横断で編集されるリポは、fetch せずに触ると分岐事故になるため。**全リポの P2 完了を待つ必要はない**——あるリポの P2 収容が済めば、そのリポの P3〜P5 には入ってよい（期限内に計画を閉じるための並行規定。tier1 の監査は第0波中から先行着火できる）。P4 のメモリ整理はリポ操作ではないため、この先行制約の対象外（2026-07-04 にこの端末分が P2 前に完了済みなのはこのため）。そして全リポを残す前提を置かない（原則4）＝再生プログラムの対象を先に絞る。

- **同期掃引スクリプト**（`bin/sync-sweep.sh`）: 走査ルートは各端末の開発ルート（この Mac は `~/Developer`。端末ごとの走査ルートは SYNC_LEDGER に記録）。全リポで `git fetch --all` → ahead/behind・dirty・unpushed・**stash 数（`git stash list`。stash は status に出ず push でも運ばれない——2026-07-04 実測で OpenCClaw の stash に CLAUDE.md 類の未収容編集が残置されていた）**・迷いブランチ・既定ブランチ名・NO_REMOTE・gitignore された非追跡ファイルの有無を台帳出力。**開発ルート直下の非 git ディレクトリも列挙して報告する**（.git の無い実プロジェクトは NO_REMOTE より無防備なのに、git 列挙だけだとトリアージの視界に入らない——2026-07-04 実測で ad-studio・blog-figmaker の2件がこの形）。
- **終活トリアージ（掃引直後・再生より先）**: 台帳＋`gh repo list` を突き合わせ、**git リポと非 git 実プロジェクトの両方**を「継続／休眠／削除候補」に仮分類して一覧でオーナーに提案→承認（常に H）。**分類基準（オーナー裁定 2026-07-04）: 「休眠」は端末単位の状態であってプロジェクトの生死ではない。ローカルが GitHub より古い（behind のみ・ローカル作業痕なし）なら「この端末では休眠」扱いでよい。プロジェクト自体の継続・引退・削除はオーナー宣言でのみ決まる——AI がローカルの鮮度からプロジェクトの死を推定してはならない。**非 git 実プロジェクトは継続なら git 化、休眠なら tar 退避が既定。承認済み削除の安全手順:
  - **安全に消せる条件（全て満たす）**: remote あり・全ブランチ push 済み・dirty ゼロ・**`git stash list` が空**・gitignore された貴重物（.env/鍵/ローカル docs/データ/CLAUDE.md 類）が無いことを実走査で確認（`git status --ignored`＋目視。push 済みリポでも gitignore 分は GitHub に無い——2026-07-04 にローカル CLAUDE.md 消失をこの盲点で実証。stash も同様に push では運ばれない）。

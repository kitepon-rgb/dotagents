# 04_ci — focused gateと最終通し試験

<!-- 前提: PLAN.md 原則1②。必要性を実証した最終確認CIの設計は最上位知能の使い所。具体モデルは docs/02_models.md で解決する。 -->

dotagents は同期ハブであり、壊れた `install.sh` や `bin` スクリプトが全端末へ配布される外部境界を持つ。変更中の動作確認は対象のfocused targetで行い、すべての関連targetがgreenになった後の最終通し試験としてだけ **`make ci`** を1回実行する（[01_project-layout.md](01_project-layout.md) 必須要件「テスト＋CI」）。`make ci`で失敗した場合は失敗機能を切り分け、最小再現とfocused targetで原因特定・修正確認を終えてから、最終確認として1回だけ再実行する。`make lint` は静的lintとhook smokeをまとめた関連gateである。

## ローカルで回す（正典）

```sh
make ci         # 最終確認: 全focused/related targetがgreenになった後に1回
make lint       # shell + python + markdown + 共通憲法 + skill/hook smoke
make lint-sh    # shellcheck: install.sh + bin/*.sh + tests/**/*.sh
make lint-js    # node --check: bin/*.mjs + lib/orchestrate/*.mjs
make lint-md    # markdownlint: 生きた正典の md
make lint-constitution # 共通憲法＋host deltaと生成物の完全一致
make lint-skills # Codex skill の静的契約
make lint-hooks # Claude / Codex hook の空打ち smoke
make test-constitution # generatorの冪等性・drift拒否・入力契約
make test-install # 隔離 HOME の install/profile/config apply（Codex CLI 必須）
make test-observer-package # sibling Observer package の隔離導入gate
make test-update  # cron 最小 PATH から NVM 配下の npm を解決
make test-oracle  # Oracle互換rollback wrapperのNode/entry/Chrome入口をOS非依存で検証（通常入口ではない）
make test-factory-reporter # factory reporter のprivacy/outbox/retry契約
make test-orchestrate # Control Record / executor contract の動的契約
```

ビルド工程は持たず、`install.sh`単体の構文確認は`bash -n install.sh`で行う。構成entryを変更した後のinstall再実行・symlink先確認・新規Claude/Codex sessionでの一覧確認はREADME「他端末セットアップ・ランブック」の受入手順に従う。

- 依存: **shellcheck**（`brew install shellcheck`）・**ripgrep (`rg`)**（skill smoke の検索入口）・**node/npx**（markdownlint-cli2 を npx 経由・バージョン固定 `@0.23.0`）・**python3**・**Codex CLI 0.144.1**（`make ci` / `make test-install` が実 parser として使う。CI は `@openai/codex@0.144.1` を明示導入）。
- 合格＝`make ci` の全ゲート exit 0・指摘 0。`make test-orchestrate`はCI必須であり、shell・mdに加えてControl Record / executor contractの動的契約を検証する。さらに`shared/constitution.md`＋host deltaとClaude／Codex生成物の完全一致、Lattice工程表SessionStart hookのCLI不在／正規status／未生成／異常系、隔離HOMEでのinstall/config applyとtransaction rollback、cron最小PATHからのNVM/npm解決、Oracle互換wrapperのOS非依存なrollback入口、factory reporterのprivacy/outbox/retry契約を検証する。通常のChatGPT入口はgpt-connector正本に従う。
- `make test-observer-package`は、`OBSERVER_REPO`（既定はsibling
  `../Observer`）をnpm tarball化し、隔離HOME／prefixだけで
  install→reinstall→verify→rollbackを検証するmulti-repo gateである。
  Observer sourceをdotagentsへ複製しないため、単独checkoutの`make ci`には
  含めず、Observer統合TODOの完了候補で独立実行する。

## shellcheck（shell）

- 対象: `install.sh`、`bin/*.sh`、`tests/**/*.sh`。既存 smoke の `A && B || C` に限る SC2015 は、テスト自身が fail 状態を集計して最後に終了する意図的な形のため除外し、他は既定ルールのまま維持する。
- shell は本数が少なく密度も低いので既定ルールで green を維持できる＝厳格側に置く。

## markdownlint（docs）— 構造検査

- 設定: [`.markdownlint-cli2.jsonc`](../.markdownlint-cli2.jsonc)（リポ直下）。対象は**生きた正典と配布 skill**＝ルート `CLAUDE.md`/`README.md`・`claude/CLAUDE.md`・`claude/skills/**/*.md`・`codex/AGENTS.md`・`codex/skills/**/*.md`・`shared/**/*.md`・`docs/**/*.md`。`docs/archive/**`（凍結）・`docs/evidence/**`（完了task証跡。Lattice evidence記述子がgit_blob_oid/content_digestで内容を束縛するため、後から編集すると証跡と食い違う）・`node_modules/**` は除外。
- 方針: **正しく描画される既存の知識文書と戦わない**。純スタイル系の4ルールだけ無効化し、構造系（見出し階層・見出し前後空行・末尾改行・ハードタブ・空リンク 等 ~40 ルール）は既定のまま残す＝将来の編集の破綻は捕まえる。
- **無効化した4ルールと根拠**（勝手に有効へ戻さない・戻すなら既存文書の一括修正とセットで裁定する）:

| ルール | 内容 | 無効化の理由 |
|---|---|---|
| MD013 | line-length（80桁） | 日本語散文＋広い表に固定桁は不適。折り返しは可読性を下げる |
| MD060 | table-column-style | 表パイプ整列の見た目のみ。意味に無関係 |
| MD040 | fenced-code-language | ASCII ツリー図・テキスト断片に言語指定は無意味 |
| MD031 | blanks-around-fences | リスト内フェンス（GitHub で正常描画）にだけ発火する摩擦 |

## 共通憲法の生成一致

- 人が編集する共通条文の唯一の正本は`shared/constitution.md`、host固有条文は`claude/CLAUDE.delta.md`と`codex/AGENTS.delta.md`に置く。
- `node bin/render-global-constitution.mjs --write`が`claude/CLAUDE.md`と`codex/AGENTS.md`を決定論的に生成する。両生成物はruntimeへ直接symlinkされるため、外部Markdownをモデル自身に読ませるfallbackを使わない。
- `bin/verify-constitution-parity.sh`はgeneratorの`--check`を呼び、生成物が正本＋deltaと完全一致しなければ非0終了する。生成物の直接編集や再生成漏れは`make lint`で拒否する。
- `node --test tests/constitution/generation.test.mjs`が冪等生成、drift拒否、不正引数拒否を動的に検証する。

## CI（[.github/workflows/ci.yml](../.github/workflows/ci.yml)）

- トリガー: `push` to `main`＋`pull_request` to `main`。手動実行時だけ単一環境を選べる。
- 最終通し試験は工場のself-hosted runner 4環境（macOS native・Linux native・Windows native・WSL2）で同時に開始し、4環境すべてで同じ製品コマンドを実行する。OSごとの役割分散はしない。
- 共通matrixは再利用workflow [`.github/workflows/factory-full-ci.yml`](../.github/workflows/factory-full-ci.yml) が所有する。各製品が渡すのは、その製品自身の最終通し試験コマンドだけである。
- CIは実装中の原因調査や修正確認には使わない。最小再現とfocused targetを該当環境でgreenにした後、最終確認として4環境fullを1回実行する。fullで失敗した場合も、次の修正効果はfocused targetで確認してからfullへ戻る。
- runnerは製品コマンドに必要なtoolchainを常備する。workflow内で都度OS別の場当たり的な導入をせず、欠落はコマンド失敗として明示する。
- dotagents自身は4環境で同じ`make ci`を実行する。`node`・`npm`・`python3`・`shellcheck`・`rg`・`codex`のversion確認も同じコマンド列に含める。
- reusable workflowは各runnerでNode.jsの`os.availableParallelism()`を読み、`FACTORY_CI_JOBS`をfull commandへ渡す。各製品のtest runnerは自身の標準並列またはこの値を使い、工場側から個別runtimeの並列flagを強制しない。OSごとの役割分散や、CPUを使うためだけの製品別job分割は行わない。
- npx が `markdownlint-cli2@0.23.0` を都度取得（固定版＝ルール変更でゲートが勝手に赤/緑にならない）。

### self-hosted runner登録・repo移転手順

workflowが`runs-on: [self-hosted, factory, <environment>]`を宣言していても、対象repoから一致するonline runnerが見えなければjobは実行されない。queuedを製品不具合として直さず、次の順でGitHub側の接続を直す。

1. 対象repoから見えるrunnerを確認する。0件または必要ラベル不足なら、製品コードとworkflowは変更せず登録作業へ戻る。

   ```sh
   gh api repos/OWNER/REPO/actions/runners \
     --jq '.runners[] | {name, status, busy, labels: [.labels[].name]}'
   ```

2. 工場runnerはorganization scopeへ登録し、runner groupが`Selected repositories`なら対象repoを追加する。runner groupのrepo accessとrunner一覧は次で照合する。

   ```sh
   gh api orgs/OWNER/actions/runner-groups
   gh api orgs/OWNER/actions/runners \
     --jq '.runners[] | {id, name, status, busy, labels: [.labels[].name]}'
   gh api orgs/OWNER/actions/runner-groups/GROUP_ID/repositories \
     --jq '.repositories[].full_name'
   ```

3. repoのowner／organization移転後は、旧scopeの登録が新repoから見えると思い込まない。各hostの既存runner serviceを止め、GitHubの対象organizationまたはrepoの`Settings → Actions → Runners → New self-hosted runner`が発行する新しい登録tokenで`config`を実行し直す。organization groupへ直接入れる時は`--runnergroup GROUP_NAME`を指定する。tokenは短命の秘密なので文書・log・shell履歴へ残さない。
4. 各hostでrunner serviceを起動し、次のcustom labelを持つonline runnerが対象repoから各1台以上見えることを確認する。

   | 実行環境 | 必須custom label |
   |---|---|
   | macOS native | `factory`, `macos-native` |
   | Linux native | `factory`, `linux-native` |
   | Windows native | `factory`, `windows-native` |
   | WSL2 | `factory`, `wsl2` |

5. `workflow_dispatch`で`environment=all`を1回実行し、4jobが同じworkflow run内で別runnerへ割り当てられ、queuedのまま残らず同時進行することを確認する。各job冒頭で`FACTORY_CI_JOBS`が1以上かつ当該processから見える論理CPU数と一致することも確認する。

登録・status・group accessの根拠はGitHub公式の[Adding self-hosted runners](https://docs.github.com/actions/how-tos/manage-runners/self-hosted-runners/add-runners)、[Monitoring and troubleshooting self-hosted runners](https://docs.github.com/actions/how-tos/manage-runners/self-hosted-runners/monitor-and-troubleshoot)、[Managing access using runner groups](https://docs.github.com/actions/hosting-your-own-runners/managing-self-hosted-runners/managing-access-to-self-hosted-runners-using-groups)とする。

## 拡張の指針

- shell/docs を足したら glob は自動で拾う（`bin/*.sh`・`docs/**/*.md`）。新しい docs サブディレクトリ（`audit-YYYY-MM/` 等）も対象に入る。
- Node.jsの配布scriptは`bin/*.mjs`と`lib/orchestrate/*.mjs`を`node --check`し、Python coreは`lib/orchestrate/*.py`を`py_compile`する。factory reporterはfake BugHubを使う動的testも通す。
- 別種の lint（yaml・json 等）を足すなら Makefile に `lint-<kind>` を増やし `lint` の依存に足す＝ローカルと CI が同時に追従する。

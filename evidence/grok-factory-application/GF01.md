# GF01 — Grok Hook / Aiterm 観測証拠

- 観測日: 2026-08-14
- 対象: Grok CLI `1.0.3 (1a29d5bc12d4) [stable]`
- 観測範囲: 登録済みHook、既存の直接実行、既存のAiterm管理実行、Aitermの完了・transcript投影
- 非実施: 設定変更、製品修理、追加のGrok実行、秘密値の保存

## 結論

Grok本体からAitermまでのrequest、terminal、answer投影は生きている。一方、dotagents projectのClaude互換Spotter hookは、Grokが渡すcamelCase入力に対してClaude形式のsnake_case `session_id`を要求し、複数イベントでexit 2になった。特にStopでは同じ応答が8回継続され、上限到達後にturnが完了した。

Aiterm管理実行 `grok46-parent-consult-smoke-20260814` は、`turn_started` 1件、`turn_ended(outcome=completed)` 1件、`aiterm-wait outcome=done`、`malformed_events=0`だった。transcriptに `AITERM_GROK46_OK` が9件並んだのはtransportの再送ではなく、初回応答とStop継続8回で作られた9 assistant messageをAitermが順に結合した結果である。

## Hook別観測

`grok inspect --json` ではprojectをtrustedとして読み込み、対象7イベントへ合計20 hookを登録していた。

| イベント | 登録 | 実行時の観測 | exit / stderr相当 | 後続動作 |
| --- | ---: | --- | --- | --- |
| SessionStart | 5 | Aiterm管理実行で各1回。Throughline以外の4件は成功 | Throughlineがexit 1。runtime記録は終了コードのみ | fail-openでpromptへ進行 |
| UserPromptSubmit | 5 | Aiterm管理実行で各1回。global 4件は成功 | project Spotterがexit 2 | passive扱いでturn開始 |
| PreToolUse | 2 | 既存のdotagents直接実行でSpotter失敗を7回観測 | Spotterがexit 2、blocked=true | tool実行を拒否 |
| PostToolUse | 2 | dotagentsではPreToolUse拒否により到達不能。別repoの既存Aiterm実行でCaveat成功を34回観測 | 観測範囲では成功 | tool結果後も継続 |
| PostToolUseFailure | 1 | 登録は確認。全ローカルsession検索では実行記録なし | 未観測 | 未観測 |
| Stop | 4 | Aiterm管理実行で各8回。Caveat / todo-gateは成功 | Throughlineはexit 1でfail-open。Spotterはexit 2、blocked=true、`hook input missing required string "session_id"` | 8回継続後、上限によりturn終了 |
| SessionEnd | 1 | 別の既存Aiterm sessionでSpotter実行を1回観測 | Spotterがexit 2 | passive扱いで終了 |

インストール済みvendor文書 `~/.grok/docs/user-guide/10-hooks.md` が示す共通入力は、`hookEventName`、`sessionId`、`cwd`、`workspaceRoot`、`timestamp`、`permissionMode` である。PreToolUseは `toolUseId`、`toolName`、`toolInput`、PostToolUseは `toolResult`、Stopは `stopHookActive`、`lastAssistantMessage` などを追加する。今回のSpotter stderrは、このcamelCase契約と `session_id` 要求の不一致を実行時にも確認した。

vendor文書上、PreToolUseのexit 2は拒否、Stopのexit 2は継続要求、それ以外の非ゼロはfail-openである。Stop継続は最大8回で、その後は強制的にturnを終了する。観測結果はこの契約と一致した。

## A / B / C 対照

| 経路 | request到達 | terminal | answer投影 | 判定 |
| --- | --- | --- | --- | --- |
| A: 既存のplain direct実行 | 4 `turn_started` を確認 | 4 `turn_ended` を確認 | Aiterm外のため対象外 | 同じSpotter schema不一致を確認。Aiterm固有ではない |
| B: 同一cwd・同一prompt・同一flagsのdirect実行 | 未観測 | 未観測 | 未観測 | 親から追加Grok実行禁止の指示があり、同値比較は作らなかった |
| C: 既存Aiterm管理実行 | 1 `turn_started` | 1 completed `turn_ended`。waitはdone / malformed 0 / exit 0 | 9 assistant messageを回収 | transport、terminal、投影は成立。Stop継続症状を再現 |

既存のdirect TUI sessionには同一条件のturnがなく、Bの代用にはしていない。したがって本証拠は「Aitermが原因ではない」ことをAとCの共通失敗から支持するが、完全な同値A/B/C比較を完了したとは主張しない。

## 原因境界

1. dotagents project SpotterはClaude互換入力を前提に `session_id` を要求し、GrokのcamelCase入力と構造的に不一致である。UserPromptSubmitとSessionEndではpassive failure、PreToolUseでは全tool拒否、Stopでは8回の不要な継続を起こした。
2. ThroughlineはSessionStartとStopでexit 1になった。Grok契約上はfail-openであり今回の完了を妨げていないが、runtime記録に詳細stderrがなく、本証拠だけでは原因を確定しない。
3. AitermのGrok完了判定はvendor `events.jsonl` の `turn_ended` を使う。今回のwait成功はHook成功ではなく、Grok turnがcompletedへ到達したことを示す。
4. AitermのGrok transcript抽出は、最後の実user row以降にあるassistant文字列を改行結合する。9回反復はこの投影が9 assistant rowを忠実に返したもので、単一最終回答へ縮約する契約ではない。

## 実測と検証

- `grok --version`: `1.0.3 (1a29d5bc12d4) [stable]`
- `grok inspect --json`: trusted project、SessionStart 5 / UserPromptSubmit 5 / PreToolUse 2 / PostToolUse 2 / PostToolUseFailure 1 / Stop 4 / SessionEnd 1
- 既存sessionのtyped event集計: Aのturn開始・終了各4件、Cのturn開始・終了各1件、CのStop継続8回を確認
- `aiterm-wait --session grok46-parent-consult-smoke-20260814 --cursor 0 --timeout 5`: outcome=done、malformed_events=0、exit 0
- Aiterm source確認: Grok completionは`turn_ended`、transcriptはassistant message列の改行結合
- Aiterm環境値・認証値は記録から除外した

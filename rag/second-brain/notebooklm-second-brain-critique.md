## 投稿の要旨（販促を剥いだ中身）

- NotebookLM は「入れたソースの中だけで考える」grounded QA（全回答に引用元）＝第二の脳に最適との主張
- 技法: ①Fast Research を3切り口で回す ②ノート毎カスタム指示で人格設計 ③自分の価値観・判断軸をソース化 ④**良い回答をソースに昇格させて「育てる」（複利）** ⑤Studio はカスタムプロンプト指定 ⑥Gemini/Gem 連携 ⑦「何を入れないか」の選球眼 ⑧匿名化・著作権・規約の線引き

## 収束の発見（ここは本物）

**「出力を知識ベースに還流させて育てる」**は、Karpathy の LLM Knowledge Bases（2026-04、filing back）と本投稿（メモのソース昇格）が**独立に同じ結論**に到達している。うちの rag/ 還流規約の裏付けが2本になった。同様に「何を入れないか」＝キュレーション規律も、うちの INDEX.md（出典・取得日・確度）と一致。

## うちの「主脳」に採用しない理由（アーキテクチャ判定）

1. **真実の置き場所が他人の器**: ノートは Google のサイロ内。素のファイルでも git でもない。Karpathy 原則「it's just files」の対極。窓（ビューア）ではなく**器（保存＋検索＋UI 一体）**なので、「依存は窓に限定」原則に反する
2. **エージェントから触れない**: 公式 API は [Enterprise 限定](https://docs.cloud.google.com/gemini/enterprise/notebooklm-enterprise/docs/api-notebooks)（2026-07 時点）。コンシューマ API は「準備中」表明のみ。[notebooklm-py](https://github.com/teng-lin/notebooklm-py) 等の非公式ラッパーはあるが規約グレー・脆い＝土台に置けない。うちの脳は Claude/Codex/Grok 全員が読めることが要件
3. 「嘘をつかない grounded QA」の便益は、**agent＋rag/ で既に同等を達成**（Karpathy: 100記事40万語をベクトルDB無しで QA）。サイロ無しで同じ便益が得られる

## 窓としてはアリ（採用するなら）

- **一方通行 git → NotebookLM**: rag/ の md をコピーとして食わせ、音声概要・スライド等**人間の消費用**に使う。脳の真実は git のまま＝NotebookLM が消えても無傷（Obsidian と同じ非搭重ポジション、ただし優先度は低い）
- 逆流（NotebookLM 内でしか育たない状態）は禁止
- 採否は P0 ツール標準化の候補リストで裁定（オーナーの好み次第・必須ではない）

## 流用する思想（ツール抜きで規約へ）

- 還流（育てる複利）・選球眼（入れない勇気）・人格＝文脈の事前注入（うちでは CLAUDE.md が既に担う）・機微情報の匿名化と規約遵守

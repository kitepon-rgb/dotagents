# audit-gauntlet

文書 (計画書・仕様書・設計書など) を 3 つの関門に通して磨き込むスキル。
書いた本人と同じ視点で見直すと盲点を再度見落とすため、各監査は独立 context のサブエージェントに投げる。

## 引数

対象ファイルのパス (絶対パス推奨)。

引数なしで呼ばれた場合は **会話文脈から対象を推定する**:
- 直前にユーザーまたは Claude が作成・編集・言及した文書ファイル
- 「この計画書を」「さっきの設計書を」のような指示語があれば、その指示先
- 推定候補が 1 つに絞れたらそれを採用し、対象を 1 行で宣言してから進める (例: 「対象: `path/to/plan.md` で進める」)
- 候補が複数ありそうな場合・推定できない場合のみ、ユーザーに対象を確認する

## 全体フロー

```
[文書]
   ↓
関門 1: 多角監査 (ECC council, 2 ラウンド固定)
   ↓
関門 2: 矛盾監査 (指摘ゼロまで収束)
   ↓
関門 3: 実現性監査 (指摘ゼロまで収束)
   ↓
[磨き上げた文書]
```

順序の根拠: 大局 → 細部の順に粒度を絞る。多角監査で構造を整えてから細部 (矛盾・実現性) を詰めると、後段の修正が振り出しに戻りにくい。

## 関門 1: 多角監査 (ECC council, 2 ラウンド固定)

ECC プラグインの `council` skill を 2 回連続で呼ぶ。

各ラウンドの手順:

1. `Skill` tool で `council` を起動。お題は「この文書を 4 voice で多角的にレビューしてほしい」。文書本文 (またはファイルパス) を渡す
2. 4 voice (Architect / Skeptic / Pragmatist / Critic) の指摘を集約
3. critical な指摘を文書に反映 (`Edit` または `Write`)。趣味レベルの提案は採否を判断
4. 修正後の文書で次のラウンドへ

**2 ラウンド固定**。3 ラウンド以上はやらない (council は決定支援用途で、無限に走らせる設計ではない)。

ECC プラグインが導入されていない環境では関門 1 をスキップせず、エラーで停止してユーザーに報告する (fallback 禁止)。

## 関門 2: 矛盾監査 (収束まで)

サブエージェント (`general-purpose`) を独立 context で起動し、矛盾だけを抽出させる。

ループ:

1. `Agent` tool で subagent を起動。prompt は次の要素を **self-contained** に書く:
   - 役割: 「文書内の矛盾を全件抽出する独立監査人。これまでの会話履歴は一切知らされていない。矛盾以外 (誤字・好み・スタイル) は対象外」
   - 対象文書全文 (または `Read` で読ませるためのファイルパス)
   - 矛盾の定義: 「同じ文書内の二箇所以上の記述が論理的に両立しない」「ある記述が文書内の他の前提と整合しない」
   - 出力形式: 矛盾リスト (該当箇所の引用 + 矛盾内容 + 重大度 critical/minor)。指摘ゼロなら「指摘なし」と明示せよ
2. 「指摘なし」が返ったら関門 3 へ
3. 指摘があれば、critical 指摘を文書に反映 (`Edit` / `Write`)
4. 1 に戻る

**収束保証**: 文書は有限テキストなので矛盾点も有限。修正サイクルを回せば必ず指摘ゼロに到達する。上限カウンタは入れない (起こりえないこと=無限ループに対策しない)。

## 関門 3: 実現性監査 (収束まで)

サブエージェント (`general-purpose`) を独立 context で起動し、実現不可能・実現困難な箇所だけを抽出させる。

ループ:

1. `Agent` tool で subagent を起動。prompt は次の要素を **self-contained** に書く:
   - 役割: 「文書内の実現性問題を全件抽出する独立監査人。これまでの会話履歴は一切知らされていない。趣味の善し悪し・矛盾の指摘は対象外」
   - 対象文書全文 (または `Read` で読ませるためのファイルパス)
   - 実現性問題の定義: 「物理的・技術的に不可能」「必要リソース (時間・コスト・人員・依存物) が現実的に存在しない」「明示された制約条件と両立しない」「前提知識が事実と異なる」
   - 出力形式: 実現性指摘リスト (該当箇所の引用 + 問題の説明 + 重大度 critical/minor)。指摘ゼロなら「指摘なし」と明示せよ
2. 「指摘なし」が返ったら完了
3. 指摘があれば、critical 指摘を文書に反映 (`Edit` / `Write`)
4. 1 に戻る

**収束保証**: 矛盾監査と同じ理由で必ず指摘ゼロに到達する。

## サブエージェント起動の注意

- 各 prompt は self-contained に書く。このスキルを呼んだ会話の流れを渡さない
- 「あなたは独立した監査人。これまでの会話履歴は知らされていない」と明示
- 評価軸 (rubric) のみを与え、修正案は求めない (修正は呼び出し側の責務)
- 並列起動はしない。各関門は順番に直列で回す (前の修正結果を次の監査が見るため)

## 完了報告

ユーザーへ簡潔に報告:

- 関門 1: 多角監査で適用した修正の要約 (1-3 行)
- 関門 2: 矛盾監査の収束ラウンド数 + 主要修正 (1-3 行)
- 関門 3: 実現性監査の収束ラウンド数 + 主要修正 (1-3 行)
- 最終的な対象ファイルパス

修正前後の diff が見たい場合は `git diff <file>` で確認できる旨を一言添える (元ファイルが git 管理下なら)。

## やらないこと

- 上限カウンタの追加 (矛盾・実現性は有限なので不要、Karpathy 原則「起こりえないことに対策しない」)
- 「念のため」の追加関門 (3 関門以外を勝手に増やさない)
- 監査結果を文書外に保存 (中間ログを残さない、必要なら git で追える)
- スタイル / 表記ゆれ / 誤字修正 (audit-gauntlet の責務外、別スキルでやる)
- 文書の全面書き直し (外科的修正に留め、指摘箇所だけを直す)
